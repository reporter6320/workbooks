    Module 1 · Lecture 1.1, 1.2 · Book §1.1

    Two ways to build a processor

    Why CPUs and GPUs are designed so differently, and why real programs use both.

    • After this module you can: define latency and throughput, explain where a CPU and a GPU spend their transistors, and decide which processor fits a given workload.

    1.1 Two measures of speed

    Picture moving people across a city. A sports car takes one passenger in 10 minutes. A bus takes 60 passengers in 30 minutes. Which is faster? It depends on what you measure:

    • Latency is the time to finish one task. The car wins (10 vs 30 minutes).
    • Throughput is the number of tasks finished per unit of time. The bus wins: 2 passengers/minute against 0.1.

    Processors face the same trade-off. A chip has a fixed budget of transistors, power and area. You can spend it on making each instruction stream finish quickly, or on running as many streams as possible at once. You cannot maximize both.

    1.2 The CPU: built for latency

    A CPU runs operating systems, browsers and compilers: code with lots of branches, pointer chasing and dependencies, where step n+1 needs the result of step n. For that code, the only way to go fast is to make one thread fast. So a CPU core spends most of its area on things that are not arithmetic:

    • Large caches (often tens of MB) so that most memory accesses never go to slow DRAM.
    • Branch prediction to guess which way an if will go and start executing before it is known.
    • Out-of-order execution to find independent instructions further ahead and run them while waiting on others.
    • High clock speed (4–5 GHz) and a handful of powerful cores (8–64).

    1.3 The GPU: built for throughput

    A GPU was first built for graphics: compute the colour of millions of pixels, each independently, 60 times per second. Nobody cares how long one pixel takes, only that all of them are done in 16 ms. So a GPU spends its area the opposite way:

    • Thousands of simple arithmetic units (2,560 on a T4, 16,896 on an H100).
    • Tiny control logic: one instruction decoder drives 32 threads at once (Module 2), and there is no branch prediction or out-of-order execution.
    • Small caches per thread. Instead of avoiding memory stalls, the GPU hides them by always having other work ready (Module 2).
    • Very high memory bandwidth (320 GB/s on a T4, about 3.35 TB/s on an H100, versus about 100 GB/s for a desktop CPU), because feeding thousands of units needs a wide pipe.

    1.4 Heterogeneous computing

    The textbook's central idea is that real applications contain both kinds of code: serial control logic (reading input, making decisions) and large data-parallel loops (the same operation on millions of elements). The best design uses each processor for what it is good at. In CUDA this is explicit:

    • The host (CPU) runs main(), does the serial parts and decides what the GPU does.
    • The device (GPU) runs kernels: functions executed by thousands of threads in parallel.
    • They have separate memories connected by a PCIe link (16–64 GB/s), so data has to be copied between them. This cost appears in every assignment.
    Worked example

    Problem. An image filter does 100 floating-point operations per pixel on a 4K image (3840 × 2160 ≈ 8.3 million pixels). A CPU core does about 4×10⁹ simple operations per second, and the T4 about 8×10¹² FP32 operations per second. Estimate the time on one CPU core and on the GPU, ignoring memory.

    1. Total work: 8.3×10⁶ pixels × 100 = 8.3×10⁸ operations.
    2. One CPU core: 8.3×10⁸ / 4×10⁹ ≈ 0.21 s.
    3. GPU at peak: 8.3×10⁸ / 8×10¹² ≈ 0.1 ms. That is 2,000× faster in theory.
    4. Reality check: the image is 8.3×10⁶ × 4 bytes ≈ 33 MB. Copying it over PCIe at ~12 GB/s takes ≈ 2.8 ms each way, about 50× longer than the computation. So the copies decide the real speed-up unless the data stays on the GPU for many operations.

    Lesson. The GPU's raw speed only pays off when there is enough work per byte moved. You will measure exactly this in Assignment 1.

    Exercises

    RecallDefine latency and throughput in one sentence each.

    Latency is the time from start to finish of a single task. Throughput is how many tasks are completed per unit of time.

    RecallName three things a CPU core spends its area on that are not arithmetic.

    Large caches, branch prediction and out-of-order execution logic (also: register renaming, deep pipelines for high clock speeds).

    ExplainWhy can a GPU get away with small caches?

    Because it tolerates memory latency instead of avoiding it. When some threads wait for memory, the hardware runs other threads that are ready. With enough threads, the arithmetic units stay busy even though each individual access is slow.

    ExplainWhy must data be copied between CPU and GPU, and why does that matter for performance?

    On a discrete GPU, host RAM and device memory are physically separate, joined by PCIe. PCIe bandwidth (tens of GB/s) is 10–100× lower than GPU memory bandwidth, so a program that copies a lot and computes little is limited by the copies, not the GPU.

    ApplyClassify each as CPU- or GPU-suited: (a) compiling a C program, (b) multiplying two 4096×4096 matrices, (c) walking a linked list, (d) training a neural network, (e) checking a password against a hash once.

(d) GPU: dominated by matrix multiplications. (e) CPU: a single small task; launching a GPU kernel and copying data would take longer than the work.

    Module 2 · Lecture 1.2

    Warps, SIMT and hiding latency

    How thousands of slow threads add up to a fast processor.

    • After this module you can: explain what a warp is, the difference between SIMD and SIMT, how latency hiding works (with numbers), and what warp divergence costs.

    2.1 The problem: memory is slow

    Reading from GPU global memory takes roughly 400–800 clock cycles. An arithmetic instruction takes about 4. If a thread computed, then waited 500 cycles for its next number, its arithmetic unit would be idle more than 99% of the time. A CPU fights this with big caches. A GPU uses a different trick.

    2.2 Warps: the unit of execution

    The GPU groups threads into bundles of 32 called warps. A warp is the real unit of scheduling: the hardware fetches and decodes one instruction and all 32 threads execute it, each on its own data. Threads 0–31 of a block form warp 0, threads 32–63 warp 1, and so on.

    This is why GPU control logic is so cheap: one decoder serves 32 threads. It is also why block sizes should be multiples of 32. A block of 48 threads makes 2 warps, the second only half full, wasting 16 lanes on every instruction.

    2.3 SIMD versus SIMT

    • SIMD (single instruction, multiple data), used in CPU vector units like AVX: one thread issues an instruction that operates on a vector register of 8 or 16 values. The programmer or compiler must pack data into vectors explicitly.
    • SIMT (single instruction, multiple threads), NVIDIA's model: you write code for one scalar thread, and every thread gets its own ID and registers. The hardware groups 32 threads into a warp and runs them together. You get SIMD efficiency while writing simple scalar code.

    2.4 Latency hiding by switching warps

    Each SM holds many warps at once (up to 32 on a T4, 64 on an H100). Every cycle, the warp scheduler picks a warp whose next instruction is ready and issues it. When warp 0 issues a memory load, it simply waits; the scheduler runs warp 1, then warp 2, and so on. By the time it cycles back, warp 0's data has arrived.

    Why is switching free? On a CPU, switching threads means saving and restoring registers to memory. On a GPU, every resident warp keeps its own registers in the SM's huge register file (65,536 32-bit registers per SM). Nothing is saved or restored; the scheduler just picks a different warp next cycle.

    Consequence: oversubscribe. You launch far more threads than there are cores (often 10–100× more), so each SM always has spare warps to switch to. A kernel with too few threads cannot hide latency, no matter how good the code is.

    2.5 How many warps are enough? (Little's law)

    Queueing theory gives a rule of thumb: the amount of work that must be in flight equals latency × throughput. If a load takes 500 cycles and the SM can issue one instruction per cycle per scheduler, you need about 500 independent instructions in flight per scheduler to never stall. Each warp contributes only a few independent instructions before it waits, so you need many warps. That is the intuition behind occupancy (Module 8).

    2.6 Warp divergence

    All 32 threads of a warp share one instruction stream. What happens with if (x > 0) A(); else B(); when some threads have x > 0 and others don't? The warp runs both paths one after the other: first A with the "else" threads masked off (idle), then B with the "if" threads masked. The results are correct; the cost is time.

    • Divergence only matters within a warp. Different warps taking different branches cost nothing extra.
    • Bounds checks like if (i < n) diverge in at most one warp (the last), so they're essentially free.
    Worked example

    Problem. A block has 128 threads. The kernel does if (threadIdx.x % 2 == 0) A(); else B(); where A takes 100 cycles and B takes 60. How long does a warp take, and how would you fix it?

    1. Warps per block: 128 / 32 = 4.
    2. Inside each warp, threads 0, 2, 4 … go to A and 1, 3, 5 … go to B. Both paths are needed in every warp.
    3. Each warp therefore takes 100 + 60 = 160 cycles instead of 100 or 60.
    4. Fix: branch on something constant across a warp, e.g. if ((threadIdx.x / 32) % 2 == 0). Now warps 0 and 2 run only A (100 cycles) and warps 1 and 3 only B (60). The work is the same but with no masked lanes. (You may need to remap which data each thread handles to keep the result the same.)

    Exercises

    RecallHow many threads are in a warp, and which threads of a block form warp 2?

    32. Warp 2 is threads 64–95 (for a 1D block).

    ExplainWhy is switching warps free on a GPU but expensive on a CPU?

    All resident warps keep their registers in the SM's register file permanently, so switching just means issuing from a different warp. A CPU core has one set of registers per hardware thread (one or two), so a context switch must save and reload state through memory.

    ExplainSIMD vs SIMT: what is the difference for the programmer?

    With SIMD you explicitly write vector operations (or rely on the compiler to vectorize). With SIMT you write normal scalar code for one thread using its index, and the hardware runs 32 such threads together.

    ApplyA block has 100 threads. How many warps, and how many lanes are wasted?

    ⌈100/32⌉ = 4 warps = 128 lanes, so 28 lanes do nothing. A block size of 96 or 128 would be better.

    ApplyA kernel launches 40 blocks of 32 threads on a T4 (40 SMs). Why will it be slow even if each thread's code is optimal?

    Each SM gets 1 block = 1 warp. When that warp waits on memory, the SM has nothing else to run, so latency is fully exposed. You need many warps per SM (dozens) to hide latency.

    ApplyDoes if (i < n) c[i] = a[i] + b[i]; cause expensive divergence?

    No. Only the single warp that straddles n has some threads in and some out, and the "else" path is empty. Every other warp is uniformly true (or uniformly false).

    Module 3 · Lecture 1.3, 1-GPU-Architecture

    Inside the GPU: SMs and the memory hierarchy

    The physical layout you are programming for, and why it shapes every optimization in this course.

    • After this module you can: describe the GPU → SM → core hierarchy, list the memory levels with their scope and speed, compute core counts and bandwidth from specs, and explain what MIG means for you on the cluster.

    3.1 The building block: the Streaming Multiprocessor

    A GPU is mostly copies of one unit, the Streaming Multiprocessor (SM). Each SM is like a small processor of its own, containing:

    • CUDA cores (FP32/INT32 units), plus FP64 units, special-function units (sin, exp, sqrt) and, on newer GPUs, Tensor Cores for matrix math.
    • Warp schedulers, usually 4 per SM, each issuing for its own set of warps.
    • A register file of 65,536 32-bit registers, shared by all resident threads.
    • Shared memory / L1 cache: a fast on-chip memory (64 KB on a T4, up to 228 KB on an H100) that blocks on this SM can use.

    When you launch a kernel, the hardware hands out thread blocks to SMs. A block runs entirely on one SM and never moves. An SM can host several blocks at once if it has enough registers, shared memory and warp slots. More SMs therefore means more blocks running at once. This is why code with many blocks automatically gets faster on bigger GPUs.

    3.3 MIG on the school cluster

    The cluster's H100s are partitioned with Multi-Instance GPU (MIG): one physical card is split into isolated slices, each with its own SMs, memory and L2 share. You get a slice (for example 16 SMs and around 10 GB), not 132 SMs. Run nvidia-smi to see what you got, and compare cluster results fairly: a MIG slice can be slower than a full T4 for some kernels.

    Worked example

    Problem. Compute the T4's peak FP32 throughput and memory bandwidth from its specs: 2,560 cores at a boost clock of 1.59 GHz, 256-bit memory bus, GDDR6 at an effective 10 Gbit/s per pin.

    1. Each core can do one fused multiply-add (FMA) per cycle, which counts as 2 FLOPs.
    2. Peak FP32 = 2,560 × 2 × 1.59×10⁹ ≈ 8.1×10¹² FLOP/s = 8.1 TFLOP/s.
    3. Bandwidth = bus width × data rate = 256 bits × 10×10⁹ /s = 2.56×10¹² bits/s ÷ 8 = 320 GB/s.
    4. Ratio: 8.1×10¹² / 320×10⁹ ≈ 25 FLOPs per byte. A kernel must do about 25 operations per byte it reads to be limited by compute rather than memory. You'll use this number in Module 4.

    Module 4 · Lecture 1 · Book §1.2–1.4

    How fast can it possibly go?

    Two back-of-the-envelope tools that predict performance before you write any code.

    • After this module you can: apply Amdahl's law, compute arithmetic intensity for a kernel, decide whether it is memory- or compute-bound, and estimate its best possible runtime.

    4.1 Amdahl's law: the serial part limits you

    Split a program's original runtime into a fraction s that stays serial and a fraction 1 − s that you speed up by a factor p. The new runtime is s + (1 − s)/p of the original, so:

    speedup = 1 / ( s + (1 − s) / p ) and as p → ∞, speedup → 1 / s

    The serial part never gets faster, so eventually it is all that is left. With 10% serial code, an infinitely fast GPU gives at most 10×. With 1%, at most 100×.

    Serial fraction sp = 10p = 100p = 1000Limit (1/s)
    0.501.8×2.0×2.0×2×
    0.105.3×9.2×9.9×10×
    0.019.2×50×91×100×

    On a GPU, host↔device copies behave like serial time, since the GPU computes nothing useful during them unless you overlap them (streams, a later lecture).

    4.2 Two ceilings: compute and memory

    A kernel is limited by whichever runs out first:

    • Compute ceiling: the GPU can't do more than its peak FLOP/s (8.1 TFLOP/s FP32 on a T4).
    • Memory ceiling: it can't move more than its peak bandwidth (320 GB/s on a T4).

    Which one you hit depends on the kernel's arithmetic intensity:

    AI = floating-point operations ÷ bytes moved to/from global memory (FLOP/byte)

    The time can't be less than either bound, so a good estimate of the best possible time is:

    t_min = max( FLOPs / peak_FLOPs , bytes / peak_bandwidth )

    The crossover is the machine balance = peak FLOP/s ÷ peak bandwidth (≈ 25 FLOP/byte on a T4, from Module 3). Kernels with AI below it are memory-bound: only moving fewer bytes helps. Above it they are compute-bound: only doing fewer or faster operations helps. Plotting attainable FLOP/s against AI gives the roofline model, which Nsight Compute can draw for your kernels.

    Worked example

    Problem. Vector add on N = 2²⁴ (16.8 million) floats on a T4. Compute the arithmetic intensity and the minimum possible kernel time.

    1. FLOPs: one addition per element, so N = 1.68×10⁷.
    2. Bytes: read a[i] and b[i], write c[i], 4 bytes each, so 12N = 2.01×10⁸ bytes.
    3. AI = N / 12N = 1/12 ≈ 0.083 FLOP/byte. That is 300× below the balance point of 25, so it is very memory-bound.
    4. Compute bound: 1.68×10⁷ / 8.1×10¹² ≈ 2 µs. Memory bound: 2.01×10⁸ / 3.2×10¹¹ ≈ 630 µs.
    5. t_min = max(2 µs, 630 µs) = 630 µs. In practice you'll measure 700–800 µs, since the GPU reaches about 80–90% of peak bandwidth.

    Lesson. For memory-bound kernels, compute speed is irrelevant: the 8 TFLOP/s are idle 99.7% of the time. This is why vector add shows the copy times dominating in your Assignment 1 chart.

    Exercises

    Module 5 · Lecture 2.1, 2.2.1

    The CUDA workflow and moving data

    The skeleton every CUDA program follows, and what each call really does.

    • After this module you can: use the three function qualifiers correctly, write the allocate → copy → launch → copy → free sequence, add error checking, and explain which calls are synchronous.

    5.1 Three questions

    Every CUDA program must answer three questions:

    1. Where does each function run? CPU or GPU, set by qualifiers.
    2. Where does each piece of data live? Host memory or device memory, set by how you allocate it.
    3. What does each thread do? Determined by the thread's index (Module 6).

    5.2 Function qualifiers

    QualifierRuns onCalled fromRules
    __global__GPUCPUA kernel. Must return void. Launched with name<<<grid, block>>>(args). Arguments are copied by value to the GPU.
    __device__GPUGPUHelper functions called from kernels, e.g. scale() and distance(). Can return values.
    __host__CPUCPUThe default for normal functions.
    __host__ __device__BothBothCompiled twice. Useful for helpers shared by a CPU reference and the GPU kernel.

    5.3 Two separate memories

    The CPU and GPU have separate address spaces. A pointer returned by malloc points to host memory; one from cudaMalloc points to device memory. They're both just float* to the compiler, so mixing them up compiles fine and fails at runtime. That's why everyone uses the naming convention h_ for host and d_ for device.

    • Dereferencing a device pointer on the CPU (d_out[0] in main) usually crashes with a segmentation fault.
    • Passing a host pointer to a kernel gives an "illegal memory access" error when the kernel runs.

    5.4 The five steps

    // 1. allocate on the GPU
float *d_a, *d_c;
cudaMalloc(&d_a, bytes);              // note: address of the pointer
cudaMalloc(&d_c, bytes);

// 2. copy inputs host → device       (dst, src, size, direction)
cudaMemcpy(d_a, h_a, bytes, cudaMemcpyHostToDevice);

// 3. launch the kernel (returns immediately!)
myKernel<<<blocks, threads>>>(d_a, d_c, n);

// 4. copy results device → host (waits for the kernel to finish first)
cudaMemcpy(h_c, d_c, bytes, cudaMemcpyDeviceToHost);

// 5. free
cudaFree(d_a); cudaFree(d_c);

    cudaMalloc takes &d_a (a pointer to your pointer) because it needs to write the device address into your variable. Its return value is reserved for an error code.

    5.5 Synchronous or asynchronous?

    The GPU has a work queue called a stream. The CPU puts operations in it, and the GPU does them in order.

    • Kernel launches are asynchronous: the CPU queues the kernel and continues immediately, often before the kernel even starts.
    • cudaMemcpy is synchronous: it waits until everything before it in the stream is finished, then does the copy, then returns. So step 4 above automatically waits for the kernel.
    • cudaDeviceSynchronize() blocks the CPU until all queued GPU work is done. You need it when nothing else waits: before stopping a timer, before checking for kernel errors, and before exiting if the kernel uses printf.
    The kernel.cu bug. The lecture's kernel.cu launches a kernel that prints, then calls cudaFree and returns. Nothing waits for the kernel, so the program can exit before the GPU's print buffer is flushed and you see no output. Adding cudaDeviceSynchronize(); after the launch fixes it.

    5.6 Error checking

    Every CUDA API call returns a cudaError_t. If you ignore it, failures are silent and you debug garbage output for hours. Wrap every call:

    #define CHECK(call) do {                                         \
    cudaError_t err = (call);                                    \
    if (err != cudaSuccess) {                                    \
        fprintf(stderr, "CUDA error %s at %s:%d\n",              \
                cudaGetErrorString(err), __FILE__, __LINE__);    \
        exit(1);                                                 \
    } } while (0)

CHECK(cudaMalloc(&d_a, bytes));
myKernel<<<g, b>>>(…);
CHECK(cudaGetLastError());        // catches bad launch configurations
CHECK(cudaDeviceSynchronize());   // catches errors during kernel execution

    Kernel launches return nothing, so there are two checks: cudaGetLastError() right after the launch catches configuration errors (too many threads per block), and the synchronize catches errors while the kernel ran (out-of-bounds accesses).

    Context creation. The first CUDA call in a program sets up the GPU context, which takes 100–200 ms. In the Lecture 2 profiles that is why cudaMalloc takes 99.9% of API time. Call cudaFree(0) once at the start to pay this cost before you start timing.

    6.1 The thread hierarchy

    A launch kernel<<<G, B>>> creates a grid of G blocks, each with B threads: G × B threads in total, all running the same kernel code. Why two levels instead of one flat list of threads?

    • Blocks are independent and can run in any order on any SM. This is what lets the same code scale from 40 SMs to 132.
    • Threads within a block can cooperate: they run on the same SM, can share __shared__ memory and can synchronize with __syncthreads(). Threads in different blocks can't.

    Inside the kernel, each thread reads four built-in variables (each has .x .y .z):

    VariableMeaningRange
    threadIdxThread's position within its block0 … blockDim − 1
    blockIdxBlock's position within the grid0 … gridDim − 1
    blockDimThreads per block (same for all blocks)set at launch
    gridDimBlocks in the gridset at launch

    6.2 The 1D global index

    Think of blocks as rows of seats in a cinema. Your seat number in the whole cinema is (row × seats per row) + your seat in the row:

    int i = blockIdx.x * blockDim.x + threadIdx.x;

    6.3 Sizing the grid: round up, then guard

    N is rarely a multiple of the block size. Integer division rounds down, so N / TPB blocks would leave the tail unprocessed. Always round up, and then make the extra threads in the last block do nothing:

    __global__ void vecAdd(const float *a, const float *b, float *c, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i >= n) return;              // guard: the last block may have spare threads
  c[i] = a[i] + b[i];
}
int TPB = 256;
int blocks = (n + TPB - 1) / TPB;   // ceiling division
vecAdd<<<blocks, TPB>>>(d_a, d_b, d_c, n);

    Why does (n + TPB − 1) / TPB round up? Adding TPB − 1 pushes any remainder over the next multiple. For n = 1000, TPB = 256: (1000 + 255)/256 = 1255/256 = 4, while 1000/256 = 3.

    Choosing TPB: use a multiple of 32 (Module 2), usually 128 or 256. Too small (32) and you hit the per-SM block limit before filling the warp slots; 1024 leaves less flexibility for the scheduler. 256 is a good default.

    6.4 Hardware limits

    • At most 1024 threads per block in total (x·y·z ≤ 1024). A block of (32, 32) is allowed; (64, 32) is not.
    • Grid size: x up to 2³¹ − 1 blocks, y and z up to 65,535.
    • Exceeding a limit doesn't crash. The launch silently fails with "invalid configuration argument", which you only see by checking cudaGetLastError().

    6.5 2D grids for 2D data

    For matrices and images, use 2D blocks and grids with the dim3 type. Map x to columns and y to rows:

    __global__ void scale2D(float *m, int W, int H, float s) {
  int c = blockIdx.x * blockDim.x + threadIdx.x;   // column  0..W-1
  int r = blockIdx.y * blockDim.y + threadIdx.y;   // row     0..H-1
  if (c >= W || r >= H) return;                    // guard BOTH dimensions
  m[r * W + c] *= s;                                // row-major: row × width + column
}
dim3 block(16, 16);                                 // 256 threads
dim3 grid((W + 15) / 16, (H + 15) / 16);            // round up each dimension
scale2D<<<grid, block>>>(d_m, W, H, 2.0f);

    Why x → column? Threads in a warp are numbered x first: threads (0,0), (1,0), (2,0) … are consecutive lanes. With x as the column, the 32 lanes of a warp access 32 adjacent floats, which the hardware combines into a few large memory transactions. This is coalescing. Swapping x and y makes the lanes access addresses W floats apart, which can be many times slower.

    #define N 64
#define TPB 32

  return ((float)i) / (n - 1);
}

  return sqrt((x2 - x1) * (x2 - x1));

  const int i = blockIdx.x * blockDim.x + threadIdx.x;   // which point am I?
  const float x = scale(i, len);
  d_out[i] = distance(x, ref);                            // write my result

    7.2 The output

    The values go 0.5, 0.484, … down to 0.0079 at i = 31 and back up to 0.5 at i = 63, the V shape of |x − 0.5|. There's no exact zero because 0.5 lies between x₃₁ = 31/63 and x₃₂ = 32/63.

    Look closely: 31 = 0.00793651 but 32 = 0.00793654. Mathematically both are 1/126. They differ in the last digits because 32/63 and 31/63 round differently in 32-bit float, and those rounding errors are visible once you subtract 0.5 (subtracting nearly equal numbers amplifies relative error).

    7.3 Why floats differ between CPU and GPU

    A float stores about 7 significant decimal digits, so nearly every operation rounds. IEEE-754 guarantees that a single add, multiply, divide or sqrt is correctly rounded on both CPU and GPU. Results can still differ because:

    • FMA: the GPU compiler fuses a*b + c into one instruction with one rounding instead of two. More accurate, but different.
    • Operation order: floating-point addition isn't associative: (a + b) + c can differ from a + (b + c). Parallel reductions sum in a different order from a CPU loop.
    • Fast math functions: with --use_fast_math, or with intrinsics like __sinf, results are approximate.
    • CPU precision: the CPU compiler may keep intermediates in higher precision or vectorize differently.

    So validate GPU results with a tolerance: fabs(gpu − cpu) <= 1e-6 * fabs(cpu) or similar, never with ==.

    8.5 Occupancy

    occupancy = active warps per SM ÷ maximum warps per SM (max = 32 on T4, 64 on H100)

    Theoretical occupancy is the best the resource limits allow. An SM's resident blocks are limited by whichever runs out first:

    1. Warp slots: max warps per SM ÷ warps per block.
    2. Block slots: max blocks per SM (16 on a T4, 32 on an H100).
    3. Registers: 65,536 ÷ (registers per thread × threads per block).
    4. Shared memory: shared memory per SM ÷ shared memory per block.

    Achieved occupancy is what was measured while the kernel ran. It's lower than theoretical when there aren't enough blocks to fill the GPU, when blocks finish unevenly, or when the kernel is so short that start-up and tail dominate.

    Worked example: compute occupancy by hand

    Problem 1. The Lecture 2 demo: <<<2, 32>>> on a T4. ncu reported 50% theoretical, 3.12% achieved. Explain both.

    1. Warps per block = 32/32 = 1.
    2. Warp-slot limit: 32/1 = 32 blocks. Block-slot limit: 16. Registers and shared memory: tiny kernel, not limiting.
    3. The tightest limit is 16 blocks × 1 warp = 16 warps; 16/32 = 50% theoretical. Tiny blocks run out of block slots before warp slots.
    4. But only 2 blocks exist for 40 SMs. A busy SM has 1 warp: 1/32 = 3.12% achieved. The fix is more work, not tuning.

    Problem 2. A kernel uses 256 threads per block and 80 registers per thread on a T4. What's the theoretical occupancy?

    1. Warps per block = 8. Warp-slot limit: 32/8 = 4 blocks. Block-slot limit: 16.
    2. Register limit: 80 × 256 = 20,480 per block; 65,536 / 20,480 = 3.2, so 3 blocks.
    3. Tightest: 3 blocks × 8 warps = 24 warps; 24/32 = 75%. (Real hardware allocates registers in chunks, so ncu may report slightly lower.) Check registers per thread with nvcc --resource-usage.
    Is higher occupancy always better? No. Occupancy is a means of hiding latency. Once there are enough warps to keep memory busy (often around 50%), more doesn't help, and some of the fastest kernels deliberately use many registers per thread at low occupancy. Treat low occupancy as a clue, not a verdict.

    9.2 Stencil: each output depends on its neighbours

    The 1D heat equation models heat diffusing along a rod. Each step, a point moves toward the average of its neighbours:

    u_new[i] = u[i] + α · ( u[i−1] − 2·u[i] + u[i+1] ) stable for α ≤ 0.5
    __global__ void heatStep(const float *u, float *u_new, int n, float alpha) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i >= n) return;
  if (i == 0 || i == n - 1) { u_new[i] = u[i]; return; }    // fixed boundary values
  u_new[i] = u[i] + alpha * (u[i-1] - 2.0f * u[i] + u[i+1]);
}
// host: iterate, swapping buffers between steps
for (int t = 0; t < steps; t++) {
  heatStep<<<blocks, TPB>>>(d_u, d_unew, n, 0.25f);
  float *tmp = d_u; d_u = d_unew; d_unew = tmp;              // swap pointers, not data
}

    Three things matter:

    • Boundaries: thread 0 has no u[-1]. Decide a rule (fixed values here) and guard it.
    • Two buffers: if a thread wrote into u while its neighbour still needs the old value, the result would depend on which thread runs first, and threads have no guaranteed order. Read from one array, write to another.
    • Synchronizing between steps: threads in different blocks can't sync with each other inside a kernel, so each time step is a separate launch. Launches in the same stream run in order, so step t+1 always sees step t's results.

    The same pattern is a 1D convolution with mask (α, 1−2α, α). General convolution uses a mask of any width.

    9.3 2D Jacobi: the 5-point stencil

    __global__ void jacobi(const float *in, float *out, int W, int H) {
  int c = blockIdx.x * blockDim.x + threadIdx.x;
  int r = blockIdx.y * blockDim.y + threadIdx.y;
  if (c < 1 || r < 1 || c >= W - 1 || r >= H - 1) return;   // skip boundary
  out[r*W + c] = 0.25f * (in[(r-1)*W + c] + in[(r+1)*W + c]
                        + in[r*W + c - 1] + in[r*W + c + 1]);
}

    Each input value is read by 4 different threads (its 4 neighbours). That reuse is wasted when every read goes to global memory. Loading a tile into shared memory once and reading it 4 times from there is the classic optimization in a later lecture.

    9.4 Matrix multiply

    C (M×P) = A (M×N) · B (N×P). Element C[r][c] is the dot product of row r of A and column c of B. One thread per element of C, with a 2D grid as in Module 6:

    __global__ void matmul(const float *A, const float *B, float *C, int M, int N, int P) {
  int c = blockIdx.x * blockDim.x + threadIdx.x;
  int r = blockIdx.y * blockDim.y + threadIdx.y;
  if (r >= M || c >= P) return;
  float sum = 0.0f;
  for (int k = 0; k < N; k++)
    sum += A[r * N + k] * B[k * P + c];
  C[r * P + c] = sum;
}
    • FLOPs: each of the M·P outputs does N multiplies and N adds: 2·M·N·P in total.
    • Global reads: each output reads N elements of A and N of B: 2·M·N·P reads, plus M·P writes.
    • Reuse: each element of A is read P times (by every thread in its row of C) and each element of B M times. A only has M·N distinct elements, so almost all reads are repeats. Tiling in shared memory removes them.
    • Access patterns: within a warp, B[k*P + c] is coalesced (c varies by lane), and A[r*N + k] is the same address for all lanes in a row, a broadcast. Both are efficient; the issue is the volume of reads, not their pattern.
    Worked example: count the work

    Problem. A is 128 × 256 and B is 256 × 32 (Assignment 1 Q2, part 2). Count FLOPs, global reads, threads and blocks with 16×16 blocks.

    1. M = 128, N = 256, P = 32. FLOPs = 2·128·256·32 = 2,097,152.
    2. Global reads = 2·M·N·P = 2,097,152 elements (8 bytes each in double = 16.8 MB of traffic, for 256 KB + 64 KB of distinct input).
    3. Grid = (⌈32/16⌉, ⌈128/16⌉) = (2, 8) = 16 blocks × 256 = 4,096 threads, all doing work (M·P = 4,096).
    4. Occupancy prediction: 16 blocks on 40 SMs means at most one 8-warp block per SM, so achieved occupancy will be low (around 25% or less). The problem is too small for the GPU.

    Why parallel, what speed-ups are realistic, and why it's hard

    10.1 The end of the free lunch (§1.1)

    Until about 2003, each new CPU ran existing programs faster because clock speeds kept rising. Then power and heat stopped that: a faster clock costs disproportionately more energy. Since then, vendors add more cores instead. A sequential program no longer gets faster on new hardware; only parallel programs do. The book calls this the concurrency revolution, and it describes two design paths:

    • Multicore (CPUs): a few cores, each keeping the full speed of a sequential processor.
    • Many-thread (GPUs): huge numbers of simple threads, optimized for total throughput (Module 1).

    The book's main motivation for learning CUDA is scalability: write code that keeps getting faster as future GPUs add more SMs.

    10.2 Why more speed? (§1.3)

    The book argues that tomorrow's mass-market applications are today's "super-applications": molecular simulation in biology and medicine, high-resolution video processing, natural user interfaces, physics-based games. They all simulate a concurrent physical world with huge amounts of data, so they're naturally parallel. Its two rules of thumb:

    • An application with data parallelism can often get a 10× speed-up with a few hours of work.
    • A good, carefully optimized GPU implementation can reach more than 100× over one CPU core.

    This is directly relevant to your programme: molecular and medical simulation is one of the book's headline examples.

    10.3 Speeding up real applications (§1.4)

    The book makes Amdahl's law (Module 4) concrete with two examples. Check them yourself:

    Parallel fractionParallel part sped upNew timeOverall speed-up
    30%100×70% + 0.3% = 70.3%≈ 1.4×
    30%∞70%1.43× at most
    99%100×1% + 0.99% = 1.99%≈ 50×

    Three further points from this section:

    • 100×+ needs more than 99.9% of the time in parallel code, and that usually requires improving the algorithm, not just porting it.
    • Straightforward ports usually saturate DRAM bandwidth and stop at around 10×. Going further means using on-chip memories (shared memory, registers) to cut DRAM accesses, then working around their limited capacity. This is the arc of the whole course.
    • Give the CPU a fair chance. Some code runs very well on CPUs. A GPU speed-up measured against a poor, single-threaded CPU baseline is misleading. Keep this in mind when you report speed-ups in your project.
    The peach model. The book pictures an application as a peach. The pit is sequential code: a large share of the source, hard to parallelize, good for CPUs, but usually a small share of the runtime. The flesh is the data-parallel portions, easy to parallelize and where the runtime goes. CUDA aims to cover as much of the flesh as possible.

    10.4 Four challenges of parallel programming (§1.5)

    "If you don't care about performance, parallel programming is very easy." The hard part is speed, and the book names four reasons:

    1. Algorithmic complexity. Some parallel algorithms do much more total work than the sequential version (they aren't work-efficient), so they can be slower on large inputs. Example: a naive parallel prefix sum does O(n log n) work against O(n) sequentially.
    2. Memory-bound execution. Many applications are limited by memory access speed rather than by instructions (Module 4), which calls for new ways of improving data access.
    3. Input sensitivity. Parallel performance varies much more with the characteristics of the input: irregular sizes, sparse structure, unpredictable data rates. This causes load imbalance and warp divergence.
    4. Recurrences. Problems naturally written as "step n depends on step n−1" need non-intuitive reformulations to parallelize, sometimes with redundant work.

    The good news: researchers have solved most of these for common patterns (reduction, scan, stencil, histogram, sparse matrix-vector product, and so on), and the rest of the book and course teaches them pattern by pattern.

    Worked example: a speed-up claim, reviewed

    Claim. "Our GPU kernel is 80× faster than the CPU loop, so our medical imaging pipeline will be about 80× faster." The kernel's loop was 85% of the CPU runtime. Moving data to and from the GPU adds 5% of the original runtime.

    1. Original time: 1 (normalized). Serial part: 0.15. Parallel part: 0.85.
    2. New time = 0.15 + 0.85/80 + 0.05 = 0.15 + 0.0106 + 0.05 = 0.2106.
    3. Overall speed-up = 1/0.2106 ≈ 4.7×, not 80×. Even with an infinitely fast kernel: 1/(0.15 + 0.05) = 5×.
    4. What to do next: profile the remaining 15% (can any of it move to the GPU?), keep data on the GPU between steps to remove copies, and check that the CPU baseline was multithreaded (§1.4's "fair chance").

    12.2 How DRAM is read: bursts

    DRAM stores each bit in a tiny capacitor, and reading a cell is slow: select a bank, open a row, select a column. The DRAM core runs at only a fraction (1/4 or 1/8) of the interface speed. To compensate, every access reads a whole burst of consecutive bytes into a buffer and sends them all. On a modern GPU the unit is a 32-byte sector, grouped into 128-byte lines.

    The consequence: reading 4 bytes costs about the same as reading the 32 bytes around them. If threads use those neighbouring bytes, the transfer is fully used. If they don't, most of the bandwidth is wasted.

    12.3 Coalescing

    All 32 threads of a warp execute a load instruction together. The hardware collects their 32 addresses and issues as few sector requests as possible. When the threads access consecutive addresses, typically array[base + threadIdx.x], the 32 floats (128 bytes) fit in 4 sectors. That's a coalesced access.

    When the addresses are spread out, the warp needs many sectors and uses only 4 bytes of each. Examples: a[threadIdx.x * stride], a column of a row-major matrix, or an array of large structs.

    efficiency = bytes the threads need ÷ bytes fetched (coalesced float: 128/128 = 100%; worst case: 128/1024 = 12.5%)

    12.4 Matrices: rows good, columns bad

    For a row-major matrix, element (r, c) is at r * cols + c. Consecutive columns are adjacent in memory and consecutive rows are cols elements apart. So:

    • If neighbouring threads (consecutive threadIdx.x) handle neighbouring columns, accesses coalesce.
    • If they handle neighbouring rows, each thread is cols × 4 bytes from the next. In the demo that's 32 KB, a different sector for every thread.

    This is the whole difference between the two kernels in 3-memory-coalescing.cu. They do the same copy; only the mapping of x and y changes. In naive matrix multiply (Module 9), threads in a warp read B[k*P + c], which is coalesced, and the same A[r*N + k], a broadcast. That's why naive matmul is still reasonable.

    12.5 Book Chapter 5: two more levers

    • Memory parallelism (§5.2). DRAM has several channels and banks that work in parallel. To use them all, many requests must be in flight at once, which is another reason to have many warps resident (Module 2's Little's law).
    • Thread granularity (§5.5). Sometimes it pays to give each thread more work, e.g. two outputs instead of one, when neighbouring threads would otherwise load the same data twice. Fewer threads, less redundant traffic.

    13.1 Why shared memory?

    In the 1D stencil out[i] = (in[i-1] - 2·in[i] + in[i+1]) / h², every input value is read from global memory by three threads. Shared memory removes that redundancy: the block loads its piece of the input once into on-chip memory, then all threads read their neighbours from there. The recipe from the lecture:

    1. Break the global array into tiles, one per block.
    2. Allocate a tile in shared memory.
    3. Fill the tile collectively: each thread loads one (or a few) elements.
    4. Synchronize, then compute using the tile.

    13.3 __syncthreads(): the block barrier

    Threads of a block run in no particular order, warp by warp. After thread 5 writes s_in[5], thread 6 can't assume thread 7 has written s_in[7] yet. __syncthreads() makes every thread in the block wait until all threads of that block have reached it. Every write before the barrier is then visible to every thread after it.

    __syncthreads()cudaDeviceSynchronize()
    Called fromGPU code (inside a kernel)CPU code
    Waits forAll threads of the same blockAll GPU work queued by the host
    Use it forShared memory is filled, or finished with, before the next phaseTiming, error checks, reading results
    The deadlock rule. Every thread of the block must reach the same __syncthreads(). If some threads return early or skip it inside an if, the behaviour is undefined: the kernel may hang or silently compute garbage. So don't put if (i >= n) return; before a barrier. Instead, let out-of-range threads load a neutral value (0) and skip only the final write.

    13.4 Halo cells

    A stencil of radius RAD needs RAD extra values on each side of the tile, called halo (or ghost) cells. The tile holds blockDim.x + 2·RAD values, and thread t stores its own value at local index s_idx = t + RAD. The first RAD threads also load the left and right halos. Here's a version that is safe at every boundary:

    #define RAD 1
__global__ void ddShared(float *out, const float *in, int n, float h) {
  extern __shared__ float s[];
  int i = blockIdx.x * blockDim.x + threadIdx.x;   // global index
  int s_idx = threadIdx.x + RAD;                   // local index
  s[s_idx] = (i < n) ? in[i] : 0.0f;               // body (0 if past the end)
  if (threadIdx.x < RAD) {                         // halos
    int L = i - RAD, R = i + blockDim.x;
    s[s_idx - RAD]        = (L >= 0) ? in[L] : 0.0f;
    s[s_idx + blockDim.x] = (R < n)  ? in[R] : 0.0f;
  }
  __syncthreads();                                 // ALL threads reach this
  if (i > 0 && i < n - 1)                           // guard only the write
    out[i] = (s[s_idx - 1] - 2.f * s[s_idx] + s[s_idx + 1]) / (h * h);
}
// launch: ddShared<<<blocks, TPB, (TPB + 2*RAD) * sizeof(float)>>>(…)
    Two bugs in the lecture slide's version. (1) It does if (i >= size) return; before __syncthreads(), which breaks the barrier in the last, partial block. (2) Thread 0 of block 0 reads d_in[i - RAD] = d_in[-1], and the last block reads past the end: out-of-bounds accesses. compute-sanitizer catches the second. Fixing both is a good oral-exam story.

    13.5 Race conditions and atomics

    The dot product example (main.cpp, kernel.cu) first has each block sum its own products in shared memory, then adds the block sum to one global result. With ATOMIC 0 it does *d_res += blockSum;. That single line is really three steps: read d_res, add, write. When two blocks do this at once:

    TimeBlock 3Block 7d_res
    1reads 128128
    2reads 128128
    3writes 128 + 64 = 192192
    4writes 128 + 64 = 192192 (should be 256)

    One update is lost. This is a race condition: the result depends on timing, so it can differ between runs and even be right sometimes, which makes it dangerous. atomicAdd(d_res, blockSum) does the read-add-write as one indivisible operation, so no update is lost. Atomics exist for add, sub, min, max, exch, CAS and bitwise operations, on int, float and (since Pascal) double.

    Cost: atomics on the same address are serialized. One atomic per block (as here) is cheap; one per thread on a single counter can be very slow. That's why we reduce within the block first.

    13.6 Doing the block sum in parallel: tree reduction

    In kernel.cu, thread 0 adds all 64 products alone while 63 threads wait, which is O(TPB) serial steps. A tree reduction halves the active threads each step, so it finishes in log₂(TPB) steps:

    __shared__ int s[TPB];                                  // TPB a power of 2
s[tid] = (idx < n) ? a[idx] * b[idx] : 0;              // 0 for threads past n
__syncthreads();
for (int stride = blockDim.x / 2; stride > 0; stride /= 2) {
  if (tid < stride) s[tid] += s[tid + stride];
  __syncthreads();                                      // outside the if: every thread reaches it
}
if (tid == 0) atomicAdd(res, s[0]);

    With stride halving from the top, active threads are always the contiguous tid < stride, so whole warps either work or idle. That avoids divergence until stride < 32.

    13.7 Bank conflicts

    Shared memory is divided into 32 banks, each 4 bytes wide; element s[i] (float) is in bank i % 32. If the 32 threads of a warp access 32 different banks (or the same word, which broadcasts), the access takes one cycle. If k threads hit different words in the same bank, it takes k cycles: a k-way bank conflict.

    • s[threadIdx.x]: conflict-free.
    • s[threadIdx.x * 2]: 2-way conflict.
    • Column of a 32×32 tile, tile[threadIdx.x][c]: every element is in the same bank, a 32-way conflict. The classic fix is padding: __shared__ float tile[32][33]; shifts each row by one bank.

    The 2D Shared Memory tutorial (needed for Assignment 3) explores exactly this with setRowReadRow (conflict-free) against setColReadCol (conflicts), using a 16 × 32 tile. Nsight Compute reports conflicts under Memory Workload Analysis.

    Worked example: find every bug in the dot product

    Tiling: convolution and matrix multiplication

    Load data into shared memory once and reuse it many times. This is the most important optimization in the course.

    • After this module you can: write basic and tiled 1D convolution, derive global read counts for both, use constant memory for a mask, explain the tiled matrix multiply phase by phase, derive its reduction in global reads, handle sizes that aren't multiples of the tile, and reason about choosing a tile size.

    14.1 1D convolution

    Convolution slides a small mask M of width MW = 2r + 1 over an input array and computes a weighted sum at every position:

    P[i] = Σ_{j=0}^{MW−1} M[j] · N[i − r + j] (N[k] = 0 when k is outside the array)

    It's used for signal and audio filtering, image blurring and edge detection, CNN layers, and stencils in simulations such as the heat equation (whose mask is [α, 1−2α, α], Module 9).

    Basic kernel: one thread per output, reading MW inputs straight from global memory:

    #define R 1                                     // example: mask width 3 (the assignment uses 5)
__constant__ float d_M[2 * R + 1];              // mask in constant memory
__global__ void conv_basic(const float *N, float *P, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i >= n) return;                           // fine here: no __syncthreads
  float sum = 0.0f;
  for (int j = -R; j <= R; j++) {
    int k = i + j;
    if (k >= 0 && k < n) sum += d_M[j + R] * N[k];   // out-of-range inputs count as 0
  }
  P[i] = sum;
}
// host: cudaMemcpyToSymbol(d_M, h_M, sizeof(h_M));

    Why constant memory for the mask? Every thread reads the same d_M[j] at the same time. Constant memory has a cache that broadcasts one value to the whole warp, so the mask costs almost no global traffic. Mention this in your report: the mask's reads are separate from the input's.

    14.2 Tiled 1D convolution

    Each input value is needed by MW different outputs. In the tiled kernel, a block loads a tile of TILE inputs plus r halo cells on each side into shared memory once, then each thread computes from shared memory. This is Module 13's halo pattern with the radius as a parameter:

    __global__ void conv_tiled(const float *N, float *P, int n) {
  extern __shared__ float s[];                      // TILE + 2R floats
  int i = blockIdx.x * blockDim.x + threadIdx.x, t = threadIdx.x;
  s[t + R] = (i < n) ? N[i] : 0.0f;
  if (t < R) {                                       // left and right halos
    int L = i - R, Rt = i + blockDim.x;
    s[t]                  = (L >= 0) ? N[L]  : 0.0f;
    s[t + blockDim.x + R] = (Rt < n) ? N[Rt] : 0.0f;
  }
  __syncthreads();
  if (i < n) {
    float sum = 0.0f;
    for (int j = 0; j < 2 * R + 1; j++) sum += d_M[j] * s[t + j];
    P[i] = sum;
  }
}
// launch: conv_tiled<<<(n+TILE-1)/TILE, TILE, (TILE + 2*R)*sizeof(float)>>>(d_N, d_P, n);

    Counting global memory accesses

    Ignoring the mask (constant cache) and the edges of the whole array:

    Global reads of NGlobal writes of P
    BasicMW per output → about MW · nn
    Tiled(TILE + 2r) per block × ⌈n/TILE⌉ blocks → about n · (1 + 2r/TILE)n

    The reduction factor is about MW / (1 + 2r/TILE). It approaches MW for large tiles, because the halo overhead 2r/TILE shrinks. At the array ends, inputs outside the array aren't read at all (they're 0), so exact counts are slightly lower. A careful report states whether it counts those.

    Real speed-ups are smaller than the count suggests. In the basic kernel, neighbouring threads read overlapping inputs, and L1/L2 caches catch many of those repeats. Tiling guarantees the reuse rather than hoping for it. On a T4 a 1D convolution is often only modestly faster tiled, and for small n launch overhead dominates both. Saying this with profiler numbers to back it is what makes an A-level answer.

    Choosing the tile size

    • TILE = threads per block here, so it must be ≤ 1024 and should be a multiple of 32.
    • Bigger tiles mean less halo overhead (2r/TILE) but fewer blocks. For n = 1024 and TILE = 1024 there's only one block, using 1 of 40 SMs.
    • Shared memory per block is (TILE + 2r) × 4 bytes, tiny for 1D, so it doesn't limit occupancy here. That matters for the assignment's question about whether more shared memory helps.
    • Decide by experiment: sweep TILE ∈ {32, 64, 128, 256, 512, 1024}, time each with events, and explain the best one with occupancy and block count.

    14.3 Tiled matrix multiplication

    Naive matmul (Module 9) reads every element of A P times and every element of B M times from global memory. Tiling exploits that a block of threads computing a T × T tile of C needs the same rows of A and columns of B.

    The kernel runs in phases. In phase p, each thread of the block loads one element of the A tile and one of the B tile into shared memory, the block synchronizes, every thread does T multiply-adds from shared memory, and the block synchronizes again before the tiles are overwritten:

    #define T 16                                        // square tile, fixed at compile time
__global__ void matmul_tiled(const float *A, const float *B, float *C, int M, int N, int P) {
  __shared__ float sA[T][T], sB[T][T];
  int tx = threadIdx.x, ty = threadIdx.y;
  int col = blockIdx.x * T + tx, row = blockIdx.y * T + ty;
  float sum = 0.0f;
  for (int p = 0; p < (N + T - 1) / T; p++) {       // phases along the shared dimension
    int aCol = p * T + tx, bRow = p * T + ty;
    sA[ty][tx] = (row < M && aCol < N) ? A[row * N + aCol] : 0.0f;   // 0-padding at edges
    sB[ty][tx] = (bRow < N && col < P) ? B[bRow * P + col] : 0.0f;
    __syncthreads();                                // tiles fully loaded
    for (int k = 0; k < T; k++) sum += sA[ty][k] * sB[k][tx];
    __syncthreads();                                // everyone done before overwrite
  }
  if (row < M && col < P) C[row * P + col] = sum;
}
dim3 block(T, T), grid((P + T - 1) / T, (M + T - 1) / T);

    Points to understand line by line:

    • Coalesced loads (corner turning). Both loads index the contiguous dimension with tx: A[row*N + p*T + tx] and B[(p*T+ty)*P + col]. Consecutive threads read consecutive addresses. The lecture calls this corner turning: the load runs along rows even though the computation uses a column of B.
    • Padding with zeros handles M, N, P that aren't multiples of T. A 0 contributes nothing to the sum. There's no early return, because of the barriers.
    • Two barriers per phase: the first so no one reads a tile before it's complete, the second so no one overwrites it while others still read.
    • Shared-memory reads: sA[ty][k] is the same for all threads in a row (broadcast); sB[k][tx] spans consecutive banks. No conflicts.

    Counting global reads

    Each element of C still needs N products, but each thread now loads only one A and one B element per phase, and there are N/T phases. So each thread loads 2N/T elements instead of 2N:

    naive: 2·M·N·P reads tiled (T×T): 2·M·N·P / T reads → T times fewer

    With T = 16 that's 16× fewer global reads, and the arithmetic intensity grows by the same factor (Module 4). For non-square tiles, work out separately how many times each A and B element is loaded: each A element is loaded once per block column of the grid, each B element once per block row. That reasoning gives you the formula for a tileX × tileY kernel.

    Tile size: the trade-offs

    TThreads / blockShared mem / block (float)Read reductionT4 notes

    162562 KB16×Usually a good balance

    Bigger tiles aren't automatically faster. Once memory traffic is low enough, the limit moves to shared-memory bandwidth, barrier stalls and occupancy, and the best T has to be measured.

    Runtime tile sizes: the assignment's tiled_gemm() takes tileX and tileY as parameters.     15.2 Matrix-vector products in an LLM

    In llama2.c, matmul(xout, x, w, n, d) computes xout = W · x, where W is d × n (row-major) and x has n entries. Generating each token calls it several times per transformer layer (the attention projections and the feed-forward layers) plus once for the output classifier. Count it with a static counter, don't guess. Unlike matrix-matrix multiply, a matrix-vector product does just 2 FLOPs per weight element loaded, so it's memory-bound (AI ≈ 0.5 FLOP/byte). Its speed is set by how fast you can stream W.

    Design 1: one thread per output row

    __global__ void matvec_row(const float *W, const float *x, float *y, int n, int d) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;          // output row
  if (i >= d) return;
  float s = 0.0f;
  for (int j = 0; j < n; j++) s += W[(size_t)i * n + j] * x[j];
  y[i] = s;
}

    Simple and correct, but check the access to W with Module 12: at each step j, consecutive threads read W[i*n + j], which are n floats apart, so the access is uncoalesced. (x[j] is a broadcast, which is fine.) For d = 288 rows there are also only 288 threads, which won't fill a GPU.

    Design 2: one warp per output row

    __global__ void matvec_warp(const float *W, const float *x, float *y, int n, int d) {
  int warp = (blockIdx.x * blockDim.x + threadIdx.x) / 32, lane = threadIdx.x % 32;
  if (warp >= d) return;                                  // whole warp exits together
  float s = 0.0f;
  for (int j = lane; j < n; j += 32)                      // lanes read consecutive W entries
    s += W[(size_t)warp * n + j] * x[j];
  for (int off = 16; off > 0; off /= 2)                   // warp reduction in registers
    s += __shfl_down_sync(0xffffffff, s, off);
  if (lane == 0) y[warp] = s;
}
// launch: d warps → blocks = (d * 32 + 255) / 256, 256 threads

    Now the 32 lanes read 32 consecutive floats of a row (coalesced), and there are 32× more threads. __shfl_down_sync lets threads of a warp read each other's registers, so the warp sums its 32 partial results in 5 steps with no shared memory and no barrier. Comparing designs 1 and 2 with ncu (sectors per request, DRAM throughput) makes a strong Module 12 story for your report.

    A third option is the library: cublasSgemv. cuBLAS assumes column-major storage, so a row-major W (d × n) looks like a column-major n × d matrix, and you pass CUBLAS_OP_T. Library calls are a legitimate optimization and a project topic.

    15.3 Why the naive port is slow

    A naive port does cudaMalloc → copy W → copy x → kernel → copy y back → cudaFree inside every call. Per call:

    • W is the same every token (model weights), yet it's re-copied each call. Copying d·n·4 bytes over PCIe takes longer than the GPU needs to read it.
    • cudaMalloc/cudaFree are slow API calls (tens to hundreds of µs) that also synchronize.
    • Each call is small, so fixed costs (launch ~5 µs, copy latency ~10 µs) dominate.

    So the GPU version can easily be slower than the CPU at first. That's expected and is the point of the exercise. nsys's cuda_api_sum and cuda_gpu_mem_time_sum tables show exactly which of these costs dominates.

    15.4 Bonus preparation: porting a particle mover

    The iPIC3D-mini bonus asks you to port mover_PC(): for every particle, interpolate the electromagnetic field at its position and push it for several sub-cycles. The structure suits a GPU well: particles are independent, so use one thread per particle, keeping its whole sub-cycling loop inside the thread. What makes it harder than vector add:

    • Structs with pointers. Particle and field data live in structs containing pointers to arrays. Copying the struct to the GPU copies only the host pointers, which are invalid there. You need a deep copy: cudaMalloc each array, copy its contents, and pass device pointers (in a device-side struct or as kernel arguments).
    • Multi-dimensional arrays. Fields may be stored as double*** on the CPU. On the GPU, use the flat contiguous array behind them (check the code for a "flat" version) and compute the index by hand.
    • Data layout. Separate arrays per component (x[], y[], …), a structure of arrays, coalesce. An array of structs doesn't (Module 12 exercise).
    • Double precision. On a T4, FP64 runs at 1/32 of FP32, so don't expect a huge speed-up there; the cluster's H100 is much better at FP64. Mention which GPU you used and why it matters.
    • Validation. Run CPU and GPU versions on the same input, compare the output files (positions, velocities, or the code's diagnostic outputs) with a tolerance, and report the maximum relative difference.
    • Timing. Report the mover's time with and without allocation and transfers, since the bonus allows them inside mover_PC_gpu(). The difference shows how much a fuller port, keeping data resident, would gain.
    Worked example: is one matvec worth a GPU?

    Problem. A matvec with d = 768, n = 768 (float). Compare the naive-port cost per call (allocate, copy W and x, kernel, copy back) with the GPU-resident version, using PCIe ≈ 12 GB/s, T4 bandwidth 320 GB/s, launch ≈ 5 µs, cudaMalloc+cudaFree ≈ 100 µs.

    1. W = 768 × 768 × 4 B = 2.36 MB. x and y = 3 KB each.
    2. Naive: alloc/free ~100 µs + copy W 2.36 MB / 12 GB/s ≈ 197 µs + small copies ~20 µs + kernel (2.36 MB / 320 GB/s ≈ 7 µs, plus launch 5 µs) ≈ 330 µs per call.
    3. CPU: 2 × 768² = 1.2 MFLOP; one core at a few GFLOP/s takes about 300–600 µs. The naive GPU port is about the same, or worse.
    4. Resident weights, reused buffers: copy x (~10 µs) + kernel (~12 µs) + copy y (~10 µs) ≈ 32 µs, about 10× faster than naive.
    5. Next step, which the project explores: keep x and y on the GPU between layers as well, so only one token's worth of data moves per step and the GPU can run kernels back to back.

    Exercises

    RecallWhy is a matrix-vector product memory-bound?

    Each weight is used once: 2 FLOPs (multiply, add) per 4-byte load, so AI ≈ 0.5 FLOP/byte, far below the T4's ~25.

    ExplainWhy is "one thread per row" uncoalesced while "one warp per row" is coalesced?

    With a thread per row, at each loop step consecutive threads read elements n floats apart, in different rows. With a warp per row, the 32 lanes read 32 consecutive floats of the same row in each step.

    ExplainWhy is it fine to return early in matvec_warp but not before a __syncthreads()?

    The condition depends only on the warp index, so all 32 lanes exit together, and __shfl_down_sync(0xffffffff, …) is only called by fully active warps. There's no block-wide barrier in the kernel, so no other warp waits for the exited one.

    ApplyThe nsys output of your naive port shows cudaMalloc 45% and cudaMemcpy 50% of API time, and kernels at 2% of GPU time. What do you change first, and what do you expect?

    Allocate once and copy weights once. Malloc/free calls drop to a few, H2D traffic per token drops to the activation vector, and tokens/s rises a lot. The kernel's share of GPU time then grows, and that is the next thing to optimize.

    ApplyYou cudaMemcpy a struct Particles { int n; double *x, *u; } to the GPU and the kernel crashes reading p->x[i]. Why, and what's the fix?

    The copied struct still holds host addresses for x and u. Allocate device arrays, copy the contents, then build a struct with the device pointers (or pass the device pointers directly as kernel arguments).

    ApplyYour GPU text output matches the CPU for 40 tokens, then differs. Bug or not?

    Probably not. A parallel reduction sums in a different order, giving tiny float differences; once two logits are nearly tied, greedy sampling can pick a different token and the texts diverge from there. Confirm by comparing matmul outputs directly: if the relative error is ~1e-6, it's rounding, not a bug.
